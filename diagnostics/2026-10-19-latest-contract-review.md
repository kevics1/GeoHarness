## P0：证据翻页返回错误身份

`src/geoharness/performance.py` 的通用包装器将业务返回 JSON 的 `operation_id` 覆盖为当前读取动作自身的 ID，`evidence_call` 也指向读取动作，而非被读取的执行。

实际链条：

1. 模型请求 Python 操作 `08495a32ead9426285ee89713c2eb0ef` 的证据；返回却标为 `da11efa67c864b52905db34487044fa0`。
2. 模型使用返回 ID 和 offset=4000 继续读取，实际读到上一条证据读取记录，仅剩 667 字符。
3. 后续继续使用这些 ID、offset=8000 或 20000，出现空内容。

这是实现错误，不应归因于模型不会翻页。嵌套 JSON 和反斜杠还放大路径抄写风险。

修复要求：保留目标身份，用不同字段区分 `execution_id` 与 `target_operation_id`；返回可直接执行的 `next_call`。正常成功结果直接返回业务摘要、具名产物和下一步引用；完整日志才分页，支持按 stdout、artifacts、schema、errors 定位。读取证据不能递归变成新的业务依赖。

## P0：交付没有可编辑 QGIS 工程的保证

整个业务目录没有 `.qgs` 或 `.qgz`。本轮所有地图使用 Python/Matplotlib 生成；交付请求 `project_dir` 为空。`geo_deliver` 的工程参数可选，只能复制已存在工程，未承担创建或缺失修复职责。配置启用 QGIS 和默认 QGIS 渲染并未约束自定义 Python 出图路径。

因此工程没有被漏复制，而是从未创建。系统仍完成文件交付，是验收契约缺口。

修复要求：制图交付默认要求可编辑工程。由同一个 QGIS 工程生成 PNG/PDF，打包真实图层、样式、标签、引线、布局、CRS 和相对路径；交付前检测缺失并触发工程装配。即使视觉仍有问题，草稿交付也应包含可修复工程。质量状态与工程是否存在分别记录。任意 Matplotlib 图片无法自动无损转成同等可编辑工程，不能用“把 PNG 加入 QGIS”冒充完成。

## P1：控制器把一个动作变成三轮对话

`_submit_plan` 对未列出的旧节点执行删除。模型提交一个新依赖节点时，遗漏旧节点便收到“依赖必须为当前计划中的其他节点”。本轮两次出现，之后模型大量使用无依赖单节点计划。

`run` 返回节点状态和操作 ID，缺少实际业务结果，模型又要调用 evidence。于是原本一次执行变成 plan → run → evidence。新增编排接口没有在这轮形成有效的依赖图，反而增加往返。任务依赖与 Python stage 依赖同时暴露也增加理解成本。

修复要求：保留持久任务图，明确区分新增、修改与整体替换；普通单步由系统自动登记执行。模型只维护一套依赖关系。执行回执同时提供结果摘要、具名产物、字段、单位、CRS 和可直接引用的结果，不要求每次翻日志。

## P1：输入、脚本环境与错误恢复不够可操作

本轮实际出现：动态读取缺少 input_refs、未知 data ref、目录误作文件、已知伴随文件未绑定、双重转义路径、假定字段不存在、普通 Python 中写 CONSOLE_RESULT，以及只为检查结果而创建 view.json/ok.json。

目前数据 ref 快照从最近 16 条输出构建，结构上存在生命周期不稳定风险；尚未证明本轮未知 ref 一定是淘汰导致，不能将其直接归因为回收。

一次 11280 字符的脚本已写出 PNG/PDF，最后调用 `write_analysis_report(... .md)` 才因要求 `.json` 失败，导致整阶段失败后再次执行。该 helper 自动产生 Markdown，但调用入口的格式要求不够直观。

修复要求：持久、带类型的产物引用替代模型抄路径；读取返回可用字段、CRS、样例、伴随引用。QGIS 与普通 Python 使用各自准确的帮助和示例；显式说明各 backend 的结果返回机制。只读表格、报告、产物检查提供直接接口。错误返回包含错误码、失败字段、期望类型、合法候选和可执行修正，不机械重试同参。保留输入保护，通过可验证的产物授权解决合法读取，不能为方便而放开整个目录。

同时，本轮模型确实犯过应由保护器拦截的错：属性表排序后，将未排序的原几何按位置回填，引发 Entity/geometry mismatch。这不是误报。需要提供按冻结实体键连接与保留几何的示例和辅助方法。

## P1：修图重写整张图，造成回归和重复分析

人工查看保存 PNG 并核对脚本：

- 第 3 版名单标题为 13 处，页面只见 1 条；名单没有正确落在右侧表区。
- 第 6 版脚本先计算纸面宽高 `aw_` / `ah_`（英寸），随后直接用于米制地图范围 `ext=[cx-aw_/2,...]`，把主图缩到数米范围。PNG 只剩大片填色，居民点消失。审图在这里发现了真实严重错误。
- 第 3 至第 8 版 `pts_all.geojson` 的 SHA256 完全相同，`pts_watch.geojson` 的 SHA256 也完全相同；每次版式修改仍重新写出分析图层和报告。

修复要求：分析产物冻结复用；制图使用固定组件与声明式设置；修订只提交布局、范围、符号或标签补丁。渲染前检查地图单位/范围与数据尺度、重点实体覆盖、名单行数和排版范围。保留上个可用工程，修补失败不替换可交付版本。像素审查负责可读性判断，不能替代这些确定性检查。

## P1：分析事实与规则没有成为所有路径的共同约束

任务标为分析必需，但没有 publish_analysis，analysis_packages 为空。最终 summary 的 analysis_status、package_integrity、project_fidelity 都是 unverified。final_answer_facts 只绑定了 13 行名单的部分统计，selection、units、标准 CRS 字段为空；最终回答包含的全部分析结论没有统一经过结果包绑定。这不足以证明所有数字错误，但证据闭环未建立。

500/1000/2000 米阈值与 A–F 分类由模型自行设计，未见业务标准或用户确认。可以作为探索性规则，但不能默认表达为正式风险等级或疏散依据。

最终地图还存在确定的语义不一致：C 类图例写“火场边界500m内”，实际计算规则为“当前火场或预测蔓延边界的最近距离≤500m”。三阶段蔓延面使用近似相同的浅橙斜线，若要比较阶段差异，难以清楚辨别。

修复要求：所有分析路径先生成统一结果包和规则说明；报告、图例和最终答复都从同一规则/统计对象产生。缺业务规则时明确提出探索性假设，真正影响决策的未知条件询问用户。核实数据事实不能等同于核实科学方法。

## P1：审图问题没有稳定的修复闭环

本轮 8 次审图均为 issues，repair_progress 均未建立。图片版本变化后没有缓存命中本身是正常现象，不能因此认定缓存坏了。本轮也不是网络超时。问题在于修图未持续绑定同一问题、对象和修复目标，无法可靠判断“修了哪个问题、是否回归、还剩什么”。

修复要求：稳定 issue_id、页面/对象引用、证据区域、严重级别、建议修复范围，以及 confirmed/dismissed/fix_verified 状态；对同一对象局部复查。修复结果不确定时保留未核验状态，不能因为下次没有提到就默认解决。需要区分真实缺陷、表达偏好与误判，避免每条风格建议都触发全图重写。

## 建议实施顺序与验收

1. 先修证据身份覆盖，验证连续翻页始终指向原始操作，且成功工具结果不依赖翻日志。
2. 收敛模型接口：持久引用、精确 backend 契约、直接只读检查、自动单步登记、任务图增量修改和结构化错误恢复。
3. 统一 QGIS 制图与交付：真实可编辑工程先于或同时于 PNG/PDF；草稿也必须带工程；离开原工作目录仍可打开且图层有效。
4. 冻结分析结果，局部修图；加入本轮名单丢行、地图单位混用、实体错位和报告后缀错误的实际回归用例。
5. 全路径统一事实和规则，补齐审图问题生命周期，再用本轮任务做端到端验收。

验收关注首次调用成功率、有效分析/修图动作比例、模型往返次数、重复分析次数、工程可编辑性和证据一致性；耗时作为结果指标，不设机械时间或调用次数截停。
