## 1. 两次初始失败

### QGIS doctor 实际成功，失败属于相邻的 Python 调用

实际 QGIS doctor 的 manifest 为 status=succeeded、exit_code=0，QGIS 版本 3.44.7-Solothurn，算法数 440。stderr 存在字体查找警告，但没有导致本次 doctor 失败。这个检查证明运行时能够启动和枚举算法，不等于所有分析、布局及字体均已业务验收。

紧邻失败 JSON 指向 runs/verify_crs_spread-20261008T110547Z-df0ab7754660，属于 geo_python。保存脚本先进行浮点几何坐标减字符串属性，再调用 astype(float)：

```python
(gx - pt.wgs84_lng).astype(float)
```

因此报 TypeError: unsupported operand type(s) for -: 'float' and 'str'。应先用 pd.to_numeric 转换字段，再做运算。真实数据最小探针复现相同错误；先转换后的最大差约 3.98e-13 度，属于浮点舍入量级。

这一结果证明几何坐标与名为 wgs84_lng/lat 的属性内部一致；仅凭这个检查不能独立证明整个数据采集和坐标转换来源正确。并行工具的终端显示容易让失败结果看起来属于相邻工具，应该按工具调用标识核对，不能根据行邻接判定归属。

### 居民点 impact 失败于发布目录，不是空间运算报错

错误发生在 analysis/vector.py 将已写入结果的 .staging-* 目录 rename 到最终目录时。工程导出后面也在同类 staging.rename(destination) 步骤失败。

最小 Windows 探针确认：子文件被其他进程持有时，目录重命名可以产生同样的 WinError 5；关闭该句柄后同一重命名成功。进程工作目录落在待移动目录或子目录中也能阻止重命名。正常关闭文件的目录重命名 100/100 成功；在独立临时目录中，真实 impact 30/30、真实工程导出 30/30 成功。

这些重复探针验证的是目录发布步骤，不代表导出的工程已通过 QGIS 读回或复杂布局验收。因此，短暂文件句柄占用是有实验支持的候选原因；原失败时没有采集句柄持有者，不能确定是哪个进程，也不能确定是杀毒软件或永久 ACL 问题。当前受限诊断进程无法读取某些以受保护 ACL 创建的临时目录，不应混同于用户终端的原始故障。

最小工程改进：关闭所有写入器后，仅对最终发布步骤的 Windows 5/32 做有限、短间隔重试；记录源/目标、尝试次数和错误码，失败仍明确返回。保留已计算结果，避免为发布问题重复空间分析或重绘。不要通过扩大权限、重置 ACL 或无限重试掩盖错误。

## 3. 空 geo_python 参数、超时限制及输出目录

### geo_python {}：调用参数无效，没有执行脚本

会话存在两次 geo_python 输入为 {}。GeoPythonInput 在执行前拒绝缺失 code，所以下方错误表示参数校验失败，不表示 Python 跑过后输出为空。

上游 OpenAI 兼容解析器在工具 arguments JSON 解码失败时也会把输入替换成 {}。离线经过真实解析器的探针表明，模型直接返回 {} 和返回截断的 {"code":"print( 都能变成同一条空输入。当前记录未保存原始 arguments，无法判定这两次属于哪一种。带无效工具调用的消息也不会触发现有“完全空消息”恢复。

改进方向是保留有界、脱敏的参数诊断或参数长度、JSON 错误位置、finish_reason，并在副作用发生前区分缺参与截断；只允许一次有明确原因的参数修复。长制图脚本应让位于结构化制图工具，避免反复传送整段脚本。

### timeout exceeds configured maximum (120s)：请求了 280 秒，被提前拒绝

对应实际调用的 timeout_seconds=280，而配置上限为 120。工具在启动脚本前拒绝这个参数，既没有实际跑满 120 秒，也没有生成这次运行目录。

目前 schema 只说“不大于配置上限”，未把当前数值 120 直接暴露给模型；这是接口信息缺口。应动态暴露上限，默认省略 timeout_seconds，并在报错中同时列出 requested=280 和 allowed=120。只有真实测量证明正常任务需要更久时，才讨论提高上限。

### map_v5_final：违反 RUN_DIR 写入约束

该脚本尝试在自己新建的 RUN_DIR 之外创建 fire_map_out，被应用级文件 guard 拒绝。这与 staging.rename 的 Windows 错误不同。工具说明已明确 RUN_DIR 是唯一输出目录，该次属于模型未遵循工具约束。

### 工程打包成功不等于 QGIS 工程坐标配置有效

10 个数据图层有效，各自 CRS 正常（晕渲为 32647，矢量为 4326），不能说整个工程没有图层。地图框 layers() 为空也不能单独证明缺图层，因为默认项目可见图层可以由 QGIS 另行取得。

实际 XML 和 project.json 都保存了 EPSG:32647；单独用 QgsCoordinateReferenceSystem.readXml 读取 projectCrs 节点会得到有效 CRS。对照原生 PyQGIS 工程后已定位直接原因：当前 project.py:700-703 手工写出的 properties 只有 Paths/Absolute，缺少 SpatialRefSys/ProjectionsEnabled。QGIS 因此没有正确启用工程投影。

独立临时副本只新增以下节点，原图层、范围与布局不改，读回的项目/地图框 CRS 即恢复为有效 EPSG:32647、单位 metres，比例尺约 1:161,082.47；原生 PyQGIS 构造的微型工程自动带有该配置，读回结果相同：

```xml
<SpatialRefSys>
  <ProjectionsEnabled type="int">1</ProjectionsEnabled>
</SpatialRefSys>
```

节点位于 properties 内。这个单变量对照确认是现有手写工程兼容性缺陷；仅检查 XML 中的 authid、manifest 或数据图层 valid 会漏掉问题。原用户工程没有被修改。

应优先复用原生 PyQGIS 工程创建和保存，并在隔离环境重新打开后验证项目/地图框 CRS、单位、范围、比例尺和实际布局。当前 project_worker.py:668 只检查图层有效性，因此这份无效项目 CRS 的工程仍得到 inspect succeeded。这个缺陷应先于复杂布局扩展修复；既有自动化通过不能替代这份工程的读回验收。

## 5. 视觉审查 ValidationError 的真实含义

首版审图在本地布局检查发现文字溢出，直接返回 issues，没有请求视觉服务。最终图第一次审查已收到 response_model、usage 和 finish_reason=tool_calls；当前代码随后在 MapReview.model_validate_json 校验审查参数时失败。这说明失败落在返回内容的结构化解析/校验阶段，不能据此称为服务宕机或确认“模型侧故障”。

报告只保存 error_type=ValidationError，没有保留具体 loc/type/msg 或原始 record_map_review 参数，无法回溯哪个字段不符合 schema。离线测试中，layout_patch=null、不支持的补丁字段和 status="pass" 都会产生 ValidationError，且现有代码压缩为同一条摘要。这些只是说明诊断缺口的例子，不是原业务原因的定论。

第二份报告 review_cached=true，复用首份失败的 8.156 秒和同一图片 digest，并未进行第二个服务请求。第二次调用增加了 evidence，但当前缓存键只有图像 digest 和 provider 配置，新增证据没有进入审查模型。模型把它写成“审查服务连续两次故障”是误读。

同配置、同 schema 的唯一一次纯合成图片请求本次成功：请求模型 none，输出 39 token、推理 0 token，9.422 秒，schema 校验通过。它证明当前管线可以正常工作，不能证明复杂地图审查能力足够，也不能解释原业务具体字段为何失败。该次网关未按 required 返回工具调用，而是返回合规 JSON 文本，现有 fallback 正常接收。

必须把 network/provider、JSON、schema、budget、cache 区分并记录；校验失败保留有界脱敏参数及具体字段错误，再针对有证据且无歧义的形式做兼容，不能先整体放宽 schema。修复不改图片的 schema 错误时，应有明确、有限的恢复通路；缓存命中要明确写“未发送新请求”。

最终 layout.json 的 passed 仅覆盖 layout_geometry，visual_review_status 与 data_correctness 仍为 unverified。颜色检出、非白比例、晕渲纹理只能支持“有内容被画出”，不能证明位置、压盖、分类、数字和坐标含义正确。

## 6. 建议优先级与验收

### P0：先让接口、发布及失败解释可靠

1. 目录发布统一关闭资源及有限重试，记录真实失败阶段；模拟持有句柄后释放时应能发布，永久失败仍返回明确错误，空间分析不重复执行。
2. 保留结构化审查具体校验错误，区分缓存与新请求；每类故障应可定位，schema 修复不能被描述为第二次服务故障。
3. 运行时公开 Python 超时数值、区分 map_path/project_output_dir，保留无效工具参数来源；校验失败应零脚本执行，恢复不重复执行已有工具。
4. 任务 ID 与阶段状态由系统管理，成图统计和方法说明从分析 manifest 生成；未执行数据准备或未完成视觉检查时不能声称完成。
5. 修复 QGIS 工程读回后的无效 CRS 与异常比例尺，复用原生工程写入；验收不能只判断文件存在或图层 valid，必须重新打开并检查坐标和布局语义。

### P1：让 QGIS 成为制图执行主路径

这次会话 79 次工具调用中有 34 次 geo_python、1 次 geo_qgis doctor，以及打包后 1 次 geo_qgis_project inspect，没有使用它创建工程或导出地图。QGIS 当前能够使用，但这次布局和出图仍由模型编写 Matplotlib 脚本；“已安装并集成 QGIS”没有自动产生默认使用 QGIS 的行为。

优先复用当前 PyQGIS 独立运行时、Processing、图层样式、标签引擎、QgsLayout 和现有工程导出工具。补齐主图/详图/图例/比例尺/说明栏模板，由模型提供结构化图层角色、分析结果引用、样式和范围，确定性代码负责 CRS、范围转换、数据类型、导出与检查。图片与可编辑工程应从同一个工程布局导出。

范围不再跨模块传递无名四元组，使用明确字段或 QgsRectangle；必要的 Matplotlib 支路用统一转换或 rasterio.plot.plotting_extent。预检应检查有序且有限的范围、图层与可视窗口相交、必需字段类型、分析与显示 CRS、预期要素及标签数量。空间语义检查与布局检查分开，像素检查不得升级为正确性结论。

这需要补齐复杂布局能力，不能宣称目前基础工程工具已经覆盖此次全部放大图与编号需求。自定义 Python 保留为确有必要的扩展入口。

### 后续模型能力评估

本次已有充分证据说明当前模型在长脚本和故障归因上表现不稳定，但尚无同题对照证明某个替代模型更合适。先减少模型自由编写 GIS 细节的职责，再用固定样例比较合法调用率、首次正确成图率、统计及说明一致性、审查缺陷检出、修复次数、耗时与成本。用户先前延后的正式质量基准仍保持后续事项。
